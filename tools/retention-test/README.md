# 本地数据保留策略验证

在仓库根目录执行：

```bash
bash tools/retention-test/run.sh
# 验证最低支持的 PostgreSQL 主版本：
RETENTION_PG_IMAGE=postgres:15 bash tools/retention-test/run.sh
```

需要 Linux Docker、bash、gzip、python3。默认使用 `postgres:18.1-alpine3.23` 和
`golang:1.27.4-alpine`，可以用 `RETENTION_PG_IMAGE` / `RETENTION_GO_IMAGE` 覆盖。
Go 构建使用命名缓存卷 `sub2api-go-mod`、`sub2api-go-build`。

脚本创建仅绑定 `127.0.0.1` 随机端口的独立数据库容器、随机数据库密码和全新数据库，
不读取部署配置、生产连接信息或生产数据。退出时删除本次数据库容器及其数据卷。
测试拒绝远程主机以及非 `sub2api_retention_test` 数据库。
Go 容器使用 host 网络访问该回环端口，仓库挂载为只读。

结果保留在 `output/retention-test/tmp-retention.*/`（已被 Git 忽略），包括测试日志、
清理前后 SQL gzip 备份、数据库/表/索引尺寸、行内容校验和、索引定义及 `result.json`。
这是可重建的数据库测试环境，不会启动网关或发送上游模型请求。

## 验证内容

1. 对空库运行项目完整迁移，再运行一次，验证幂等性及新增索引有效性。
2. 使用迁移后的表定义，在隔离 schema 内验证严格到期边界、多批次删除、
   `pending/applied/blocked` 和空完成时间保护、同请求不同 Key 的独立去重。
3. 故意让归档插入违反约束，验证热表删除会回滚；通过锁等待触发取消，验证重试能完成。
4. 验证关闭开关会跳过清理，以及数据库 advisory lock 防止多个实例同时执行。
5. 对真实迁移表注入 60 天 × 每天 1,000 行 × 五张表的合成数据，另加少量保护记录。
   JSON 载荷是每行不同的约 1 KiB 哈希文本，专用于可重复的备份实验。
6. 调用实际清理 worker，验证以下显式配置的短保留策略（不是程序默认值），并验证重复执行不会继续删除：

| 数据 | 保留策略 | 清理后主样本数 |
|---|---|---:|
| 请求诊断 | 3 天 | 3,000 |
| 耗时明细 | 3 天 | 3,000 |
| 完成计费事件 | 7 天，按完成时间 | 7,000，另保留 3 条未完成事件 |
| 计费去重热表 | 15 天 | 15,000，另 1 条重放检查记录 |
| 计费去重归档 | 原始请求时间起合计 30 天 | 15,000，另 1 条重放检查记录 |
| 流量明细 | 7 天 | 7,000 |

7. 检查用户余额、20 天前的请求明细和流量小时汇总仍保留；使用实际计费仓储重放热表、
   归档中的请求，不会重复扣款；不同指纹返回冲突。
8. 检查清理前后所有索引定义和有效状态不变，检查普通 `VACUUM (ANALYZE)` 后数据和索引不变。
9. 将清理后 gzip 备份恢复到空库，比较保留数据的行数及完整内容校验和，
   比较所有索引的身份/有效状态及本次保留策略相关索引的完整定义；重新验证迁移与去重。

隔离 schema 的 `LIKE ... INCLUDING ALL` 保留列、约束和索引，但不会复制触发器与外键；
完整 worker、备份恢复及计费重放实验使用真实迁移表，保留其触发器与外键。
备份恢复可能将其他历史索引中的表达式转成等价形式，因此不对无关索引的 SQL 文本做逐字比较。

## 尺寸结果的含义

仅在这个临时容器中关闭 autovacuum，以稳定区分 DELETE、手动普通 VACUUM 和恢复三个阶段。
没有运行 `VACUUM FULL`、`REINDEX`，没有修改生产 autovacuum 配置。

逻辑备份会立即排除已删除行。DELETE 后物理占用可能暂时不变，归档写入还可能增加占用；
普通 VACUUM 回收死元组供后续写入复用，某些表的连续空尾页可被截断，但不保证表或索引文件整体缩小。
恢复到空库会重新构建表和索引，因此通常更紧凑。

本实验验证正确性和上述空间行为。合成数据的压缩率、保留比例、耗时不能直接用于预测生产库
或 boscserver 的备份大小；首次清理大表的 WAL、IO 和业务负载影响也需要在部署时单独观察。
