# 使用月报

新版 Sub2API 内置月报。分别在 boscserver（主站）和 ecosserver（独立站）打开 **运维监控 → 设置 → 评估报告配置**，填写本站报告收件人，开启报告总开关和「月度评估报告（Excel）」并保存。新开关默认关闭。北京时间每月 1 日 06:15，各站从自己的 PostgreSQL 汇总上个自然月的已入账用量，给每个收件人单独发送一封含 Excel 的邮件。上传附件时，每完成一块数据写入就重新计 20 秒，等待最终回执也有 20 秒时限，且受月报任务总时限约束。它沿用站内 SMTP，无需另装导出器；xs199 不运行此任务，从站补交的用量在主站账本中。

启用当月为首个统计月；若在北京时间 1 日启用，则从刚结束的月份开始。重启后会检查已到期但未处理的月份，按先后顺序补发。附件含用户身份信息，收件人只取评估报告名单，不回退到告警地址或管理员。相同月份和收件人的投递记录存于本站数据库。SMTP 明确拒绝时按小时重试；若发出后回执丢失则记录异常并保留领取记录，不盲目重发。查看后台任务 `ops_monthly_usage_report` 的运行记录和同名月报服务日志标识 `[OpsMonthlyUsage]`。

**从旧版 systemd 定时器切换：** 在各权威站部署带此功能的版本后，先确认旧发送服务空闲、评估报告邮箱和 SMTP 配置正确，再停用旧定时器（`systemctl disable --now sub2api-monthly-usage.timer`），随即启用内置月报。保留旧归档及投递凭证。若当日是 1 日且旧任务已发过上月报告，等到 2 日再开启新开关，以免两个独立发送器对同一月份重复发信。回退时先关闭内置月报；重新启用旧定时器前，对照旧归档和新投递记录核对待发月份，避免旧任务自动补发已投递邮件。

**手动发送：** 在同一配置区保存收件人和报告总开关后，选择一个已经结束的北京时间自然月（默认上月），点击发送。月报自动开关可保持关闭。后台按当前账本和用户资料重新生成三页 Excel，不会使用历史归档替代可能已清理的明细。页面区分 SMTP 已受理、明确失败和回执不明；关闭页面不会取消已受理的任务。手动任务不改变定时计划，若明确再次发起，同一月份可以再发一份。

每份工作簿只有三张表：

| Sheet | 粒度与口径 |
|---|---|
| 明细 | 北京时间日期 × 用户 ID × 请求模型；含用户名、当前真实姓名、当前所属部门和日志的实际使用分组。 |
| 部门月汇总 | 每个部门一行，含注册且未被封禁人数、当月活跃用户数。即使当月无人请求，只要有符合条件的注册用户，部门也会列出。按导出时的完整部门路径归属，每人只计一次；空部门汇入“未填写部门”。 |
| 用户月汇总 | 每个活跃用户 ID 一行，跨天与模型相加；同名账户分开。 |

三张表和注册人数使用同一部门字段。默认按用户先取 `dingtalk_department`，为空时再取 `department`；旧版独立导出器沿用此默认规则。内置月报也可指定一个已启用、未删除的文本、多行文本或单选属性。指定后只读该定义 ID，用户未填写时按空部门统计；若生成时定义已停用、删除或改成不支持的类型，本次生成会报错并停止发送。

文本和多行文本保留字段内容，去掉首尾空格。单选字段用保存的原值精确匹配当前选项并显示标签；选项已移除或标签为空时显示保存的原值。标签和原值在输出时均去掉首尾空格，相同显示名合并统计。

人数和用量在同一个只读数据库快照中导出。根据本站用户 ID 和导出时的角色，三张表均排除管理员（包括已软删除的管理员）的用量，注册人数也排除管理员。注册人数按北京时间下月 1 日零时前已注册、导出时未删除、状态为启用且未被当前生效的整用户网关封禁来统计，含零请求账号；不把仅限平台、会话、Key 或 IP 的限制当作整账号封禁；这不是对月末封禁状态的历史还原。活跃用户按排除管理员后的当月用量日志统计，保留已停用、被封禁或软删除的普通用户的历史用量，两个指标不一定存在包含关系。

三张表的表头统一为 32 磅，可分两行显示；数据行统一为 20 磅，垂直居中。部门、姓名、分组和模型列按本站本表的数据分布取宽，少数长值不会撑宽整列；选中单元格可在编辑栏查看全文。数字列按格式化后的数值留宽，同表的四个 Token 列等宽，便于横向比较。部门汇总的 Token 以 B（10⁹）为单位，用户汇总以 M（10⁶）为单位，单元格存换算后的值。通常显示三位小数，更小的非零值显示更多位。两张汇总表先按各自维度累计实际费用再向零截断到整数美元，因此各行整数之和不一定等于全站扣费。明细保留原始 Token 和扣费。

三张表显示请求数、输入 Token、输出 Token、缓存读取 Token、总 Token 和用户扣费（美元）。总 Token 沿用账本口径，包含未单列的缓存创建量。超过 Excel 15 位有效数字的个别值直接在原单元格以文本保真，不另加列。费用只取 `actual_cost`，是含订阅用量的用户实际计费等值，不代表现金支付流水。用户资料取导出时值；不导出账户邮箱。请求模型缺失时回退到日志记录的模型。请求数不含未记入用量账本的失败尝试；已丢失的明细或尚未入账的请求不分摊到部门和用户。月报包含用户身份资料，须限制归档和邮件的访问。

## 旧版独立导出器：安装、首次生成与补发

要求 Linux、systemd、Docker 和 Python ≥ 3.9（含亚洲时区数据），本机已有 Sub2API 数据库容器 `sub2api-postgres`，Sub2API 后台已配置 SMTP。邮件读取本站当前 SMTP 设置，465 使用隐式 TLS，其他端口强制 STARTTLS；仅向单独配置的运维收件人发信。任务需要在本机读 Docker socket，仅以管理员身份安装受信任的源码。

1. 创建 `/etc/sub2api-monthly-usage.json`，root:root、0600，内容形如 `{"site":"boscserver","first_month":"2026-10","recipient":"owner@example.org"}`。独立站填 `ecosserver`。起始月必须是计划补发的第一个月。收件地址仅存在本机私有配置，不提交到 Git。
2. 在本站运行 `sh install.sh`，再用 `systemctl list-timers sub2api-monthly-usage.timer` 确认下次触发。任务使用北京时间，不依赖宿主机时区。
3. 立即导出已结束的月份（不发信）：`python3 -B /opt/sub2api-monthly-usage/report.py render 2026-10`。归档位于 `/var/lib/sub2api-monthly-usage/Sub2API-<site>-YYYY-MM.xlsx`，目录 0700，文件 0600；临时 CSV 在正常退出后删除。手动发送：`python3 -B /opt/sub2api-monthly-usage/report.py send 2026-10`。
4. 立即依计划补发所有欠报：`systemctl start sub2api-monthly-usage.service`。停机错过执行由持久定时器补触发，程序从起始月份检查每个已结束月份，已受理的不重复发送。用 `journalctl -u sub2api-monthly-usage.service` 查看结果。

旧导出器生成 XLSX 时，同时写入同名 `.render.json`，记录报表口径版本、文件名和附件 SHA-256。首次投递（含修订版）会核对三项；缺少凭证、版本过旧或内容不符时，会按当前账本重算并替换该归档。即使旧附件已有三张表，也可能含管理员数据。若需保留升级前未投递的原件，应在启动定时器或手动发送前另存一份；历史明细若已清理，重算只能反映仍在账本中的用量。

同名 `.delivery.json` 优先于归档检查。旧版和新版的 `accepted` 都表示发件 SMTP 已受理，程序会跳过该份报告；`sending` 会阻止自动重发，并保留对应附件。手工与定时任务共用文件锁。SMTP 返回 `354` 后才开始传正文。正文结束后，只有 `250` 记为已受理，明确的 4xx / 5xx 拒绝可重试；断线或异常回执保留 `sending`。可重试的失败由 systemd 一小时后重试。遇到 `sending`，先用 Message-ID 核对邮件侧记录，确认未受理后再移走标记并运行 `send`。

修订已投递月份时，运行 `report.py render YYYY-MM --revision 2`，核对生成的工作簿，再运行 `report.py send YYYY-MM --revision 2`。修订附件、生成凭证和发送标记均使用独立的 `-r2` 后缀。可用 `--note` 在修订邮件中说明已知统计缺口。归档含用户身份资料，请限制访问，按本地保留策略清理附件并保留发送标记。

卸载定时任务：`systemctl disable --now sub2api-monthly-usage.timer`，停止同名 service 后移除专用的两个 unit 文件，执行 `systemctl daemon-reload`。归档和投递状态需要单独保留或按需清理。

## 验证

在本目录运行 `python3 -B -m unittest discover -v`。SQL 集成测试需要已缓存的 `postgres:16` 镜像，在独立无网络容器内验证真正的 PostgreSQL 查询。其余用例不需访问生产或发送真实邮件。
