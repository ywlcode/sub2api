## 调度和协议

- 多分组 Key 保留同一个选组入口和账号池。用户配置的分组顺序优先，选中分组继续走既有排队/并发逻辑；不为没人使用的负载排名扫描整批账号。保留本分支每 Key 最多 5 组、模型发现、WebSocket 首帧和订阅/权限逻辑；上游的余额不足分类只在其他请求策略通过后返回 403。
- 保留上游 GPT‑6.2 Sol/Astra 的兼容请求缓存标识、模型不可用的 WebSocket 错误帧以及流终态/错误处理。缓存标识只帮助上游识别相同前缀，不改变上游报告的命中 token 或用户账单。保留定制的 200/400/409 恢复边界和火山 DeepSeek 三协议原生处理。
- 数据清理维持单一入口，使用上游传入的时区确定保留边界。不会因为删除旧凭证模块而关闭其他清理或新增从站管理后台。

滚动升级测试见 `tests/site-lab/test_upgrade_2230.py`：新主配旧从实际发起三协议请求和 GPT 转发，核对旧账单、停从期间主站可用；升级从站后验证定价全量补齐、增量修改、恢复默认值及删除。部署按 ecosserver、boscserver、xs199 的顺序，每台验收有效流终态并独立观察两分钟，再进入下一台。

## 本次验证

- 除本地 CI 的 Go 单测、真实 PostgreSQL/Redis 集成、竞态测试、前端全量测试和构建外，还验证了回退：保留新数据库及迁移记录，分别换回旧从站和旧主站，主站直连、从站本地和 gzip 转发均收到完整响应。仅覆盖本次 6 个加法迁移，不是对以后迁移的回退保证。
- 真实 Codex、Claude Code、OpenCode、dsh 共 7 个客户端与模型组合，140 轮、343 次 HTTP 请求；工具写入的结果文件和压缩后的跨轮信息均通过校验。Codex 对 GPT 发出 3 个远端压缩触发并得到 3 个压缩条目，对 DeepSeek 发出 3 个摘要提示请求。dsh 有 37 次按客户端自己的大小检查放弃替换摘要；两模型共 20 次成功压缩，没有一轮因此中断。Claude Code 的 GPT Messages 不在此次范围。
- 完全阻断实验主从链路，第 1,192 秒从站仍就绪，第 1,201 秒首次观察到失效：新的本地和转发请求均为 503，断网前开始的 1,218 秒流正常结束。恢复连接后两笔账单入账，余额一致、outbox 清空。另测 60% 丢包加 140 ms 延迟，8 个本地流均完成。
- 隔离基准使用 400 个用户，每个站点应用限 2 vCPU / 8 GiB，输入 100,000 个英文词，模拟上游延迟 1.5 秒、输出预算 3,000。新旧版本各 4,000 个计时流全部正常结束（不含预热），两端逐用户对账一致。预热后 220 并发，主站 / 从站本地 / 从站 gzip 的首个可见内容 P95 分别由 7.67 / 7.49 / 9.45 秒变为 7.57 / 7.31 / 9.22 秒；冷缓存 220 并发从站本地为 7.70 → 7.68 秒。采样的应用内存峰值主站 786 → 942 MiB，从站 1,068 → 1,016 MiB；这是一次运行的容器采样，不代表长期占用或公网首字保证。
