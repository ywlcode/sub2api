# 主从同步复审修复

基线：`4464df8ff`。用户指出的两处问题均成立，上一轮验证未覆盖持续扣费与导出事务交叠，以及人工补扣后解除从站保留扣款的场景。

## 导出与并发扣费

原实现通过 `REPEATABLE READ` 事务删除 `site_changes`，会与正在更新同一变更行的扣费触发器冲突，并把行锁持有到快照提交。原重试退避总计 310 ms，不包括 SQL 运行与锁等待，不能消除这个争用。PostgreSQL 对快照内更新已被其他事务修改的行的处理见[事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)，锁的持有期见[锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)。

修复使用精确变更版本：在同一快照中读取变更版本、业务数据和回执；只持久化导出投影，不更新或锁住业务变更队列。快照发布后，通过短事务、`SKIP LOCKED` 和版本相等条件清理已处理项。快照期间的新提交、持锁未提交事务，以及删除后重新插入的同名项都会留给下一轮。清理失败只导致重复导出，不会漏同步。

多个主站实例先取得该从站专用的发布锁，再开始快照；扣费不用这把锁。连接异常时丢弃仍可能持锁的连接，不把它放回连接池。导出仍需写入自己的投影和版本表，业务表与变更队列在构建快照期间只读。

迁移 342 给变更集合增加版本标识；已有行使用常量默认值，避免给整张旧队列执行序列填充重写。序列仅作为相等比较标识，不作为提交顺序或高水位游标。

## 拒收账单与人工对账

- 时钟超前、账号/订阅依赖缺失，以及外键/唯一约束冲突进入 `retrying`，30 秒后重试。失败事件通过保存点回滚，其余账单可继续处理；未入账事件不会取得成功计费回执，也不占用 4,096 条待核对回执窗口。
- 确定性错误进入 `pending`。原始账单、原因及从站原扣款覆盖继续保留，等待明确处理。
- 主站新增管理员对账 API，支持 `retry`、`settled`、`waived`。前者重试原始账单；后两者分别表示已核实手工结清和明确免收，本身不再次扣款。要求备注，保存处理时间和操作者，相同终态操作幂等，冲突操作返回 409。
- 处理终态通过 `$settlements` 元数据与主站余额在同一快照下发，从站原子撤销原扣款覆盖。后续同步、丢失响应和迟到的拒收消息不会重新叠加已处理账单。终态记录不再参与未结账单回放。

迁移 343 保留旧拒收记录并默认设为 `pending`，管理员可通过新 API 重试或结清，不自动假定旧账单已经补扣。协议升级为 v5，主从需要匹配版本。接口路径与操作语义见 [SITES.md](../deploy/SITES.md#拒收账单对账)。

## 验证

后端全量单测、构建、lint、站点与管理路由针对性竞态测试通过。主从存储集成测试覆盖：

- 导出回调中更新同一用户余额，写入不等待导出结束；新版本在下一轮同步。
- 未提交的变更行被清理阶段跳过；失败导出不消费变更。
- 两个主站实例同时执行 640 次同用户扣费与 80 次导出，全部成功，最终余额一致。
- 上传在快照开始后提交，回执延后到下轮，余额覆盖始终一致。
- 时钟超前事件与正常账单同批处理、延后重试成功、成功响应丢失后自动收敛。
- 账号删除后失败、修复后重试；旧永久拒收记录通过管理员操作恢复入账且只扣一次。
- 手工补扣后结清、免收、相同操作重复提交、冲突操作、迟到拒收响应与原始证据保留。
- 原有百万诊断积压、约 38.9 MB 分页快照、授权撤销、订阅周期及耗时关联回归。
