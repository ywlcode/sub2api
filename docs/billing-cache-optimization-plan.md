# 计费缓存与查询优化方案

状态：讨论方案，未实现。`/auth/me`、页面轮询和 RPM 空配置缓存属于已实现的独立优化，不改变本文讨论的扣费行为。

## 当前行为

`usage_billing_delivery.go` 在数据库中先持久化计费事件，再在事务中执行去重、金额更新、报价与用量写入，提交后失效 Redis，最后把事件标记 complete。恢复任务可以重复执行失效，但不能重复执行 Redis 金额减法，否则无法区分“上次已扣 Redis、确认结果丢失”和“上次未扣 Redis”。

因此，虽然 Redis 余额/订阅用量设置约 5 分钟 TTL，每笔收费后都会失效，下一批请求仍会回源。订阅身份 L1 与 Redis 订阅用量缓存是不同层，不能只延长一个 TTL 来解决。

## A：先减少现有流程的不必要查询

1. 余额冷读使用专用 `SELECT balance`，保留删除等过滤条件；不再通过完整用户仓库连带读取允许分组。
2. 订阅用量冷读使用专用 DTO，只取状态、到期时间、日/周/月用量及版本；不再 eager-load 分组，调用者已有分组限制配置。订阅身份与权限检查仍保留原路径。
3. 订阅用量缓存未命中增加 singleflight，并让回源的短超时上下文与第一个客户端的取消分离；减少同一用户/分组并发击穿。Redis 失败策略及资格检查不变。
4. 新计费事件 INSERT 成功且确认插入 1 行时，不再 SELECT 同一事件核对刚写入的命令。只有幂等键冲突才读取并校验已有不可变内容；COMMIT 结果不确定时仍从新连接核验，不能假定失败后重扣。

第 4 点按 2026-11-07 北京时间 00:00～20:00 的 113,954 笔正常计费，理论上可少 113,954 次 SELECT。余额/订阅 DTO 在冷读时通常各少一条关联查询；没有缓存未命中计数，不能给出全天精确节省量。此阶段不需要改变金额存储或引入新的计费一致性协议。

## B：数据库提交后同步带版本的绝对快照

目标是让正常请求完成扣费后，缓存直接得到“扣后的余额/用量”，减少 DEL 后的反复回源。

1. 为稳定账务主体增加数据库单调版本。金额变化与版本增加在同一事务、同一原子更新中完成，利用 RETURNING 拿到已提交结果的快照数据。
2. 提交后用 Redis Lua 按版本比较，写入绝对值；较旧结果不能覆盖较新结果。重复投递同一版本不再扣一次钱。金额沿用数据库规范精度，Lua 不承担账务浮点计算。
3. 将缓存同步凭据与结果放入现有可靠计费事件/通知机制。同步失败保留待恢复状态，恢复只同步快照，不重跑模型、不重复扣费。确认后才标记 complete。
4. 充值、退款、管理员改余额、订阅日/周/月重置、续期、撤销/恢复等所有修改入口必须更新对应版本并通知。订阅更换或重建须有稳定的主体版本或额外 generation，不能让新订阅的低版本被旧订阅覆盖。
5. 缓存 MISS 与旧回源并发时必须有写入栅栏；不能看到 key 不存在就接受一个延迟到达的旧快照。Redis 重启/淘汰、失效标记过期、提交后进程崩溃都要进入受控重建。普通 `version >= current` 的 Lua 比较本身不能解决这些情况。
6. 通知或 Redis 异常时，沿用明确的数据库回源/不可用策略，不使用无限期旧快照。版本解决结果顺序与重放问题，不替代并发在途额度预留、权限撤销和实时准入检查。

现有订阅 `Version` 来自 `UpdatedAt.Unix()`，秒级时间戳在并发写入时可能相同，不适合作为新协议的唯一顺序依据。此阶段需要数据库迁移、所有写入口清点及故障注入验证；应与 A 分开提交、验证和上线。

## 验证与衡量

- A：验证新事件/重复事件/指纹冲突/不确定提交；余额与订阅薄查询的过滤语义；同主体并发回源和取消隔离。
- B：验证同主体并发扣费、乱序通知、重复通知、充值与扣费交错、额度重置、订阅替换、旧回源覆盖新值、Redis 重启/淘汰、不同崩溃位置和跨实例恢复。断言数据库只扣一次、Redis 最终收敛、额度不足不能因旧缓存被扩大放行。
- 记录各缓存 hit/miss/load/invalidate、同步失败/重试/延迟、计费 SQL 调用与耗时。以相近流量比较，不用“少几条 SQL”直接推算整机 CPU 降幅。

建议先实施 A；B 的正确性条件更广，单独完成方案和测试后再推进。
